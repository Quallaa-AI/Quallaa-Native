## Starting from the right foundation saves critical weeks

The Theia IDE template at github.com/eclipse-theia/theia-ide provides everything needed for a commercial desktop IDE product. Unlike forking the main Theia platform (which creates massive maintenance overhead), the template is purpose-built for rebranding with **pre-configured electron-builder, code signing infrastructure, auto-update system, and example branding extensions**. This architectural choice alone saves 3-4 weeks compared to building from the Theia platform packages.

Theia's architecture separates frontend (browser/Electron window) and backend (Node.js server) processes that communicate via JSON-RPC over WebSockets. The **dependency injection system using InversifyJS** allows clean customization through rebinding rather than code modification—essential for maintaining separation between EPL-licensed code and proprietary extensions. The codebase organizes by platform: `common/` for shared code, `browser/` and `electron-browser/` for frontend, `node/` and `electron-node/` for backend. Extensions contribute through well-defined interfaces like CommandContribution, MenuContribution, and WidgetFactory.

The template includes a monorepo structure with Yarn workspaces and Lerna managing multiple packages: `applications/electron/` contains the desktop app with packaging configuration, `applications/browser/` provides web deployment options, and `theia-extensions/` houses custom extensions including the critical `product/` extension where branding customizations live. This structure maintains **clear boundaries between open source foundations and proprietary additions**, which is essential for both legal compliance and technical maintainability.

## Rebranding requires just 10 core file modifications for MVP

The minimal viable rebrand focuses on user-visible changes in approximately **10 key files** that can be modified in 2-3 days. In `applications/electron/package.json`, update the `name` field to "quallaa", set `theia.frontend.config.applicationName` to "Quallaa", change the preferences directory to `.quallaa`, and configure `build.productName` and `build.appId` with your company identifiers. The `electron-builder.yml` file needs matching updates for `appId`, `productName`, and `copyright` notices.

Visual branding assets go in `applications/electron/resources/`: **icons.icns for macOS** (512x512@2x), **icon.ico for Windows** (256x256), and a `icons/` folder with PNG files for Linux (16x16 through 512x512). The splash screen can be customized by creating `resources/splash.html` and configuring display options in package.json. These icon files are the most visible brand elements—users see them in the dock, taskbar, and installers before ever opening the application.

The branding extension in `theia-extensions/product/src/browser/` requires creating custom versions of key UI components. Rebind AboutDialog to your QuallaaAboutDialog that displays your branding, copyright, and license information. Override GettingStartedWidget to create a QuallaaGettingStartedWidget with your welcome content, getting started guides, and links. Update the EnvVariablesServer to change the configuration directory from `.theia-blueprint` to `.quallaa`. Finally, perform global text replacements: "Theia IDE" → "Quallaa", "Theia Blueprint" → "Quallaa", and all package names from `@theia-blueprint/*` to `@quallaa/*`.

## EPL 2.0 permits commercial products when properly structured

The Eclipse Public License 2.0 grants **broad rights for commercial use** including reproduction, modification, distribution, and sublicensing. The critical distinction: EPL 2.0 implements weak copyleft at the **file level, not project-wide**. Modified Theia source files must remain available under EPL 2.0, but proprietary extensions in separate files can use any license including closed source. This architectural separation is what enables commercial Theia-based products like Arduino IDE 2.0, ARM mbed Studio, and Google Cloud Shell Editor.

Section 3.1b explicitly permits distributing binaries under different license terms "at least as protective of the Recipient as the EPL." This means your **compiled Quallaa application can have proprietary licensing** for your extensions while maintaining EPL 2.0 compliance for the Theia components. Unlike AGPL which treats network use as distribution requiring source disclosure, EPL 2.0 does NOT consider SaaS deployment as distribution—you can offer Quallaa as a hosted service without disclosing proprietary modifications, only the EPL-licensed base components.

Attribution requirements are straightforward but mandatory. You must **preserve all existing copyright, patent, trademark, and attribution notices** in forked Theia code. Add your company copyright to new files: "Copyright © 2025 [Your Company]". For modified files, include both the original Eclipse Foundation copyright and yours. The About dialog and product documentation must state "Built on Eclipse Theia" with appropriate trademark symbols, include the full EPL 2.0 license text in LICENSE-EPL.txt, and provide clear instructions for obtaining the EPL-licensed source code (typically a GitHub repository link).

The critical compliance checklist for launch includes: maintaining all copyright headers in Theia files, including LICENSE-EPL.txt and NOTICE files in your distribution, providing a public repository with your EPL-licensed code modifications, adding "About" dialog with license information and source code links, and ensuring no use of "Theia" in your product name (Eclipse Foundation actively enforces trademarks). Pre-launch legal review by an open source attorney costs $5,000-15,000 for initial audit but prevents costly compliance failures. The EPL 2.0's business-friendly nature means **litigation risk is low** when following this checklist—no major EPL court cases exist, unlike GPL's contentious history.

## Structure proprietary features as separate modules for legal clarity

The recommended architecture maintains **crystal-clear separation** between EPL-licensed and proprietary code. Your repository structure should have: `theia-core/` (EPL 2.0) containing your fork of Eclipse Theia, `theia-extensions/` (EPL 2.0) with your modifications to existing Theia functionality, and `quallaa-proprietary/` (Commercial License) containing enterprise features, AI assistant integrations, and custom domain-specific tools. This separation isn't just good architecture—it's **legal necessity** under EPL 2.0's file-based copyleft scope.

Proprietary extensions should interact exclusively through Theia's well-defined extension APIs and dependency injection system. For AI integration, create a modular extension at `theia-extensions/ai-agent/` with clear interfaces: `common/ai-protocol.ts` defines AI service interfaces, `browser/ai-widget.tsx` provides UI for interactions, `node/ai-service.ts` implements backend AI services. This service-based architecture allows **proprietary AI models and logic** to remain closed source while the integration layer respects EPL 2.0 boundaries. The command-based interface pattern provides clean separation: public commands for user interactions, private services for proprietary implementation.

For domain-specific features targeting financial analysts, scientists, or other experts, create separate extension packages: `quallaa-finance/` for financial modeling tools, `quallaa-scientific/` for research workflow automation, `quallaa-analytics/` for data analysis features. Each domain extension can be **entirely proprietary** because they're separate modules, not modifications of Theia files. This architecture also enables flexible business models: free tier gets base Theia, professional tier adds domain extensions, enterprise tier gets custom fine-tuning and integrations.

Real-world examples validate this approach. Arduino IDE 2.0 combines EPL-licensed Theia base with proprietary Arduino hardware integrations and board management. ARM mbed Studio uses Theia foundation with proprietary embedded development tooling and hardware-specific debugging. Google Cloud Shell Editor integrates Theia with proprietary Google Cloud Platform services. These successful commercial products demonstrate that **proper architectural separation enables thriving proprietary businesses** on EPL 2.0 foundations.

## Build system and CI/CD accelerate multi-platform delivery

Theia IDE uses **Yarn workspaces combined with Lerna** for monorepo management. Yarn workspaces handle dependency hoisting and linking local packages (single node_modules at root, faster installs, easy inter-package dependencies). Lerna provides commands to run operations across all packages (parallel builds, version management, publishing). This combination is battle-tested for large TypeScript projects and requires minimal configuration—don't replace it with custom solutions.

The build commands are straightforward: `yarn install` for dependencies, `yarn build` for development builds, `yarn watch` for hot-reload during development, and `cd applications/electron && yarn package` for creating installers. The packaging step uses **electron-builder**, which handles the complex tasks of code signing, creating installers (DMG for Mac, NSIS/portable for Windows, AppImage/DEB for Linux), and configuring auto-updates. The electron-builder.yml configuration file controls all these aspects—customize appId, productName, and platform-specific settings here.

GitHub Actions provides **free multi-platform builds** for public repositories and reasonable pricing for private ones. A single workflow file at `.github/workflows/build.yml` can build on macOS, Windows, and Linux runners simultaneously using a matrix strategy. This solves the major problem of needing multiple physical machines for testing—push code, get builds for all platforms in 20-30 minutes. Critical secrets to configure: MAC_CERTS and MAC_CERTS_PASSWORD for macOS signing, APPLE_ID credentials for notarization (required for macOS distribution), Windows code signing certificate, and GitHub token for release artifact uploads.

Code signing is **non-negotiable for macOS** (apps won't run without notarization) and strongly recommended for Windows (users see scary warnings without it). Obtaining certificates requires: Apple Developer Program membership ($99/year) for Mac, certificate from a trusted Certificate Authority for Windows ($100-400/year for code signing certificate). The signing process happens automatically during electron-builder packaging if certificates are properly configured. Budget 1-2 days for certificate setup and troubleshooting—this is a common friction point where builds succeed locally but fail in CI/CD.

## Legal compliance requires minimal time but cannot be skipped

Day 1 legal setup takes 3-5 days total time but must happen before distribution. Register a business entity—**LLC recommended over sole proprietorship** because it protects personal assets from business liabilities. Cost is $100-500 for online filing in most US states. File trademark application immediately with USPTO for "Quallaa" name and logo ($250-400 per class); approval takes 6-12 months but filing establishes priority date. Early trademark filing **prevents costly rebranding** if another company files first.

Privacy policies are legally required under GDPR (EU users) and CCPA (California users), and effectively necessary for any product. Required disclosures: what user data you collect (usage telemetry, error reports, account information), third-party services used (analytics, AI providers, cloud hosting), user rights (data access, deletion, portability, opt-out mechanisms), and data retention periods. Templates from Termly or iubenda cost $0-200 and can be customized in 2-3 hours. Terms of Service must include acceptable use policy, warranty disclaimers, limitation of liability, and intellectual property provisions. EULA for installed software adds distribution terms and installation grants.

EPL 2.0 compliance checklist for every release: LICENSE-EPL.txt file in distribution with full license text, NOTICE file listing all open source components and their licenses, public GitHub repository with modified Theia source code, clear statement in About dialog "Built on Eclipse Theia" with Eclipse trademark acknowledgment, link to source code repository in Help menu and product documentation, and preservation of all original copyright headers. **Failure to provide source access is license violation** that can result in loss of distribution rights and legal liability.

The 15-minute compliance test: Can a user download your product, find the license information, access the source code for EPL components, and verify attributions? If any step fails, you're non-compliant. Set up automated checks: CI/CD validates LICENSE files present, code review checks copyright headers maintained, release checklist confirms source repository updated. Prevention costs **hours of setup**; remediation after violation costs weeks and legal fees.
